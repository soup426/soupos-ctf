soupOS — Feature Roadmap
========================
A 32-bit hobby OS written in C and NASM.
Current version: v0.60.154

Features are grouped roughly by effort. Nothing here is required;
everything is just "it would be funny/cool to build."

v0.60.149 (2026-10-09)  — A POINTER A PROGRAM NEVER HAD (FIX)
  - Any program could panic the machine: user_ok checked only that a
    pointer was inside the user range, so SYS_WRITE from 0xC6000000
    (above the break) or 0xC2000000 (between the image and the heap),
    and SYS_READ or SYS_STAT into 0xC6000000, faulted in the kernel's
    own copy; the demand pager declined and isr.c panicked. All four
    did, proven with prod.elf before the fix.
  - user_ok now also wants every page: mapped, or one the pager would
    give on first touch (the heap below the break, the stack above its
    guard). Such a call gives -1. Checked before the copy, not caught in
    the fault: by then the call may hold FAT's or the desktop's lock.
  - prod.elf (a poke with a fork) and scripts/prod-test.sh: all four
    give -1, the program ends normally, no panic, the shell goes on.

v0.60.148 (2026-10-09)  — TALLY WITH DECIMALS (seq)
  - FIRST, STEP and LAST may have fractions (0.5, .5, 1., -.25). No
    floating point in ring 3, so each is a 64-bit integer in units of the
    finest fraction typed; every value is FIRST plus whole STEPs, exact,
    and stops past LAST. Printed with as many decimals as FIRST or STEP
    has, LAST's not counted (seq 1 1.50 prints 1), as GNU seq does. -w
    is seq's arithmetic on the typed strings ("1." one narrower, ".5" one
    wider, each widened or narrowed to the printed decimals). 17 digits

  - seq-test.sh: 36 more forms against GNU seq, 57 in all (negatives,
    steps that miss LAST, counting down, -w and -s with decimals, 3001
    lines of 0.001). They now run from one script on the disk (. /SEQ.SH):

v0.43.0 (2026-10-07)  — SWAP KEEPS THE WORKING SET (APPROXIMATE LRU)
  Fifth queue, item 3. A story of two wrong turns, both caught by measuring.
  - GLOBAL PRESSURE has an arithmetic answer: eight processes at the
    1,024-page cap is 32 MB against a PMM of about 120 MB, so user
    processes cannot empty it. No mechanism built; recorded here.
  - THE VICTIM. hotcold.elf keeps a hot set used every round and sweeps
    new pages it never revisits. Under FIFO the hot set is always the
    oldest mapped, so it is evicted every round and fetched straight back.
  - Clock (second chance on the accessed bit) was tried first and changed
    nothing - 3,584 page-ins either way - though it gave 8,152 second
    chances, so the bits worked. It is the known weakness: the hot set is
    used in one phase and the sweep runs in another, the hand laps the
    resident set within a sweep, and a page cleared on one lap is evicted
    on the next. Clock approximates LRU only within one revolution.
  - Approximate LRU then: every 32 evictions each resident page's accessed
    bit is read and cleared and a used page is stamped with the epoch; the
    victim is the page with the oldest stamp. It first measured WORSE with
    a sample before every eviction. A model of the exact algorithm on the
    host matched the kernel to the page once given the heap's real cap
    (1,017, not 1,024: the image and stack count too), which showed the
    first workload was the bug - hot plus one sweep was 1,024 pages, a
    hair over memory, and a loop just larger than memory is LRU's worst
    case. Resized to 400 + 400, the model predicted and the kernel
    measured: FIFO 1,200 page-ins in 45 ticks, approximate LRU 400 in 31
    (clock, in the model, 800). Both sampling rates give the same result;
    32 is kept as the cheaper.
  - The boot segment runs hotcold and requires fewer than 600 page-ins:
    FIFO's 1,200 would fail it. lazy.elf's sweep is unchanged (a sweep has
    no working set to keep). Gate 95.

v0.39.0 (2026-10-07)  — BUS-MASTER DMA: SWAP UNDER KVM 58x FASTER
  Fourth queue, item 5b, which turned out not to be what it said.
  - The queue blamed polling: a vCPU hammering the status port while the
    host does the I/O. Two hypotheses were tested in a copy of the tree
    before anything was built. Dropping the cache flush after each write:
    4786 ticks to 4682, 2%. Halting until the drive's IRQ 14 instead of
    spinning, with interrupts turned on in the fault path: 4801, nothing.
  - THEN IT WAS MEASURED. TSC timestamps around each phase of every
    multi-sector command during the greedy swap run, under KVM: issue
    0.9 G cycles, BSY wait 16 G, DRQ wait 0.7 G, flush 3.4 G, and the data
    transfer itself 120.7 G - 85% of the run. 23 million words at about
    5,200 cycles each: KVM takes one VM exit per 16-bit word on this port,

    and moves every read and write by DMA through a 4 KB, 4 KB-aligned
    bounce buffer with a one-entry PRD table (kernel memory is identity-
    mapped, so its address is its physical address). Completion is the
    engine stopping and the drive not busy: a dozen port accesses per
    request instead of 2,048 per page. PIO remains the fallback.
  - The greedy run under KVM: 4872 ticks to 84, with all 7173 page-outs
    and 4096 page-ins verified by the program. Every FAT test, mtools'
    reading of what soupOS wrote, and the self-test's write/read/delete
    balance all pass on the DMA path. Gate 91.
  - Not done, and now a small matter: interrupt-driven completion. The

v0.35.0 (2026-10-07)  — SWAP: MEMORY THE MACHINE DOES NOT HAVE, KEPT ON DISK
  Fourth queue, item 1. v0.33.0 killed a process at the page cap; now it
  keeps going.
  - THE SWAP AREA IS THE DISK PAST THE VOLUME. The Makefile makes a 48 MB
    image and formats the first 32 MB; the 16 MB after it, 4096 pages, is
    addressed by slot (eight sectors each) with no on-disk format at all,
    found at boot from fat_volume_sectors() and ata_total_sectors(). A
    disk with nothing past the volume has no swap and behaves as before.
    (An existing disk.img is the old 32 MB one: `rm disk.img && make
    disk`.)
  - Per process: a FIFO of its resident heap pages, oldest mapped first
    as the victim, and a table from heap page to slot. At the cap, the
    fault handler writes the oldest page straight from its user address
    with one eight-sector command, unmaps it, frees the frame, and maps
    the new one; a fault on a page with a slot maps a frame and reads it
    back, evicting first if it must. Both happen in the faulting task's
    context with only the ATA mutex taken, which nothing holds while
    touching user memory, so the ring-0 case (a syscall copying into a
    swapped page) is safe too.
  - PROVEN BY lazy.elf: `greedy` touches all 4096 pages of its 16 MB and
    completes, with every page holding its value: 7173 pages out, 4096
    back in (the first pass evicts 3072, the verify pass brings each one
    back and evicts another). `absurd` claims 32 MB, more than the cap
    and the swap together, and is killed when the swap is full with
    "no page for 0x... swap 4096 of 4096". Every exit returns to the same
    free-page count. Five new checks in the boot segment, and kitchen
    shows swap in use. The exit line now also carries elapsed ticks.
  - MEASURED: under the gate's emulated boot the greedy run takes 296
    ticks, about 11,000 page transfers in three seconds. Under KVM the
    same run takes 5601 ticks, 56 seconds, nineteen times slower, because
    every port access the driver polls on is a VM exit; that is a finding
    for the queue (interrupt-driven ATA completion), not a swap matter.
  - Global pressure, the PMM itself empty, still fails the map; only the
    per-process cap evicts. The queue says which step that is. Gate 88.

v0.33.0 (2026-10-07)  — MEMORY THE MACHINE DOES NOT HAVE, YET
  Queue item 8, the honest small version: demand paging for the heap.
  - sbrk no longer maps anything. It moves the break, checks it will not
    run into the stack, and returns. A page gets a frame the first time
    something touches it, in usermode_demand_page: a page fault whose
    address lies in the running process's heap below its break, and whose
    error says "not present" rather than "protected", is answered with a
    zeroed page and the faulting instruction is retried. Any other fault
    is the fault it always was: a ring-3 one kills the program, a ring-0
    one is still a panic.
  - THE HOOK SITS AHEAD OF BOTH. The kernel touches user memory too, when
    a syscall copies into a buffer the program has only sbrk'd, and that
    fault arrives from ring 0. lazy.elf's third mode is exactly that: a
    read() into a page it never wrote. Before the hook was moved in front
    of the panic path, that would have taken the machine down; it now
    reads 64 bytes of README.TXT into a page that did not exist a moment
    earlier.
  - The cap (1024 pages a process) applies at touch time, not at sbrk.
    So lazy.elf can claim 16 MB, four times the cap, and touch one page
    in sixty-four for free; the greedy run touches every page, meets the
    cap at 4 MB, and is killed with "[demand] no page for 0x...", which is
    the honest answer to a program wanting memory the machine does not
    have. The shell goes on, and the two hello.elf runs that follow end at
    the same free-page count, so the killed process's 1024 pages came
    back. crash.elf, the fault that was never a heap page, still kills.
  - Each process counts its faulted-in pages and the exit line reports
    them ("[demand] /lazy.elf faulted in 64 pages on first touch"). Six
    checks in the boot segment. Swapping to disk is the item after this
    one, as the queue said. Gate 85.

v0.29.0 (2026-10-07)  — THE VAULT: SSH TRANSPORT AND KEY EXCHANGE
  Stage S6. A real OpenSSH client now talks to soupOS encrypted.
  - src/ssh.c: RFC 4253 version exchange and binary packets; KEXINIT
    offering one of everything (curve25519-sha256, ssh-ed25519,
    chacha20-poly1305@openssh.com); the ECDH reply signed with the host
    key; NEWKEYS; then SERVICE_ACCEPT and a userauth refusal that names

  - The host key is a 32-byte Ed25519 seed at /HOSTKEY.ED, made from the

    composition held without a single wire-level fault; that is what the
    vectors were for. scripts/ssh-test.sh asserts all of it plus the

v0.27.0 (2026-10-07)  — KILL REACHES A PROCESS BLOCKED IN THE KERNEL
  The hog the gate never killed (found in v0.26.0), fixed at the root.
  - proc_kill set the flag and relied on the process reaching a safe point
    to notice. A process blocked in a pipe read never does: it sits on the
    pipe's wait queue until its peer writes, and if the peer is the thing
    you are trying to get rid of, that is never. So `kill %` on
    `hog.elf | wc.elf &` flagged wc, wc stayed parked AND stayed the newest
    process, the second `kill %` flagged it again, and hog ran on at 90%.
  - Now a task records which queue it is parked on (task_t.blocked_on),
    and proc_kill pulls a running-but-blocked target off it with
    task_unblock. Every block site in the kernel loops and re-checks its
    condition, so an early wake is safe at all of them; the pipe loops
    already check the kill flag and return, and the syscall exit does the
    teardown. Reproduced before, verified after: wc dies on the first
    kill, the second reaches the hog, `ps` shows neither.
  - Two new gate checks assert exactly that. The gate's back half no
    longer runs under a hog, which is also the likeliest cause of the
    flaky job-control check (queue item 1); watch it.
  - A DETOUR WORTH RECORDING: the first build of this fix hung the shell
    the moment a process trapped, and so did a build with only the new
    field and no logic. The kernel stacks were at the same addresses as
    before, which ruled out heap layout and pointed at the build: the
    Makefile had no header dependencies, so editing task.h recompiled
    task.c alone and left twenty-two other objects with the old struct
    layout. -MMD/-MP with -include fixes that; touching task.h now
    rebuilds 23 objects. The lesson, for the next time an unrelated-
    looking change "breaks" the kernel: make clean first.
  - Gate 74.

v0.24.0 (2026-10-07)  — AN ENTROPY POOL
  Stage S2. Key generation needs bytes nobody can predict, and a kernel
  that boots identically every time has almost none; this matters more
  than any of the ciphers.
  - src/random.c: a 32-byte pool folded through SHA-256. Fed by RDRAND
    when CPUID says the CPU has it (mixed into every output block, not
    only at boot), the TSC at every timer tick and keyboard interrupt, and
    the RTC once. The interrupt side is one XOR into a 16-word block; the
    hash runs only when the block wraps, about six times a second.
  - Output is hash(pool, counter, tsc, rdrand), and the pool is re-hashed
    after every draw so a leaked output does not give away earlier ones.
  - THERE IS NO TEST VECTOR FOR RANDOMNESS, so the checks are the ones
    that exist: `sample` requires two draws to differ and 64 KB of output
    to sit within three sigma on a monobit and a runs count (measured:

v0.14.0 (2026-10-07)  — THE FRAMEBUFFER IS THE DEFAULT, AND DOOM RENDERS INTO IT
  soupOS now boots to a 1024x768 framebuffer with a glyph-rendered console,
  and mode 13h programs scale into it. FB=0 still builds the text-mode kernel,
  which is the only way to get real mode 13h hardware.
  - THE SAME TRICK AS THE TEXT CONSOLE, ONE LAYER DOWN. vga13h's pixel store
    became a pointer: the real 0xA0000 on a text boot, a RAM shadow on a
    framebuffer boot. Doom already rendered into its own backbuffer and copied
    to hardware in exactly ONE place, so redirecting that one copy was the
    whole integration. vga13h_present() scales 320x200 up by 3 - the largest
    whole multiple that fits 1024x768 - through a software copy of the palette.
  - The scaler builds each row once into a line buffer and lays it down three
    times, so the palette lookup happens once per SOURCE pixel instead of once
    per destination pixel, and the writes to video memory stay sequential.
  - vga13h_enter/exit now hand the screen over: the console stops painting (it
    would otherwise draw text over Doom thirty times a second) and every cell
    is marked dirty on the way back, because what is underneath is no longer
    the text we last drew. Any mode 13h program gets this for free.
  - TASKS CAN DECLARE THEMSELVES SERVICES. Doom asks for the machine to itself,
    and with a console renderer and a sound mixer always running the answer was
    permanently no. task_count_users() ignores tasks that called
    task_set_service(), which is the number that question actually wants.
  - PALETTE PRECISION, FOUND BY COMPARING FRAMES. Widening 6 bits to 8 is bit
    replication, (v<<2)|(v>>4), not a plain <<2: the latter leaves full scale
    at 252 and every bright colour a shade dark. Found by comparing a
    framebuffer frame against a mode 13h frame pixel by pixel - agreement went
    from 42% to 99.97%. The remaining 18 pixels of 64000 are a three-row band
    that differs by 13 levels, which is an animated strip between two separate
    runs.
  - DELIBERATELY NOT bit-identical to QEMU: its VGA renders odd 6-bit values as
    (v<<2)|3, replicating the low bit, which is an emulator artefact. Matching
    it would make the comparison exact and the colours wrong, so
    scripts/doom-fb-test.sh carries a 4-level tolerance and says why. A real
    fault - wrong scale, wrong offset, swapped channels, unshadowed palette -

v0.13.0 (2026-10-07)  — THE MIXER: SEVERAL SOUNDS AT ONCE
  Night-queue item 8's third milestone, and the last open item in the queue.
  The AC97 plays exactly one stream, so overlapping sounds are summed in
  software: four voices into one cyclic ring.
  - A voice is either a Doom lump kept in its RAW form - unsigned 8-bit at the
    lump's own rate, resampled on the way out - or a generated tone, which is
    a phase accumulator and no storage at all. Keeping lumps raw makes a slot
    64 KB instead of 200. A fifth sound steals the oldest voice.

v0.11.0 (2026-10-07)  — SOUND: AC97, AND A TONE THAT IS MEASURED
  Night-queue item 8, first milestone. The PCI groundwork from the network card
  was most of it: find the device, enable bus mastering, read two BARs.
  - What is different is the shape of the DMA. The RTL8139 takes one buffer per
    packet; AC97 reads a BUFFER DESCRIPTOR LIST of up to 32 entries, each
    naming a block of samples, and walks it itself. Hand it the list, say which
    entry is last, set the run bit.
  - `whistle <hz> <ms>` plays a sine through it (`beep` remains the PC
    speaker). Boot reports the card and its rate.
  - THE BUG THE MEASUREMENT CAUGHT, which is the whole reason the queue said to
    verify this on the host rather than by ear. The phase accumulator's full
    32-bit range is one period, so the step is hz * 2^32 / rate; I wrote 2^24.
    That plays a 1.7 Hz wave: inaudible, full amplitude, and indistinguishable
    from silence by ear. The capture showed it immediately - a signal with NO
    zero crossings in 0.39 s and no spectral peak anywhere near 440 Hz. After
    the fix: 440.00 Hz measured over 172 periods, with 60x the power of its
    neighbouring bins.
  - The step is computed as hz * (0xFFFFFFFF / rate) so every operation stays
    32-bit and the kernel needs no 64-bit division helper.
  - Volume on AC97 is attenuation, so 0 is loudest and 0x8000 is mute, which
    reads backwards from every other volume control in existence.
  - A descriptor's length is a count of SAMPLES, not bytes and not frames.
    Getting it wrong plays the right sound at the wrong speed, which is easy to
    mistake for a sample-rate problem.
  - Gate 62 -> 64 checks: one that the card accepted the tone, and one that
    runs on the HOST over the samples QEMU captured (-audiodev wav) and asserts

v0.10.2 (2026-10-07)  — spawn(): A SCRIPT FUNCTION AS A TASK
  Night-queue item 6, finished. This is what the context work was for.
  - spawn("worker") runs a no-argument soupyc function on a task of its own and
    returns the task id, which `ps` lists and `kill` accepts.
  - THE LIFETIME DECISION. The child gets an INDEPENDENT COPY of the code, not
    a borrowed pointer into the parent's node pool. Borrowing would have been
    a memcpy cheaper, but soupyc_run frees the parent context on the way out,
    so the child could not then outlive the `soup` command - and the shell
    getting its prompt back while the child keeps printing is the entire point.
    Node links all point inside one contiguous pool, so copying it and adding
    a fixed delta to every link relocates the whole tree; string literals live
    in the string store rather than the pool, so each is re-interned into the
    child's own store.
  - sleep(ms) as well, bounded at 10 s. A spinning child would work, since the
    scheduler preempts, but it would burn the machine to do it.
  - The struct members now carry an m_ prefix. Code that holds a context
    pointer explicitly - the clone, the child's entry - has to say ctx->m_x,
    and without the prefix the bare name expanded into the member position.
    Same class of collision as sc_state.pool in v0.10.1, now impossible.
  - Gate 54 -> 59 checks, and they test the properties rather than the happy
    path: that spawn returns an id, that `ps` catches the child mid-flight
    (which is the proof it outlived its parent), that the parent's arrays
    survive the child allocating its own and vice versa (the pool is shared,
    with per-context ownership of slots), and that the child finishes.
  - Nothing was wrong with `ps` - it lists blocked tasks fine. My first two
    attempts to see the child there ran `ps` at the exact moment the child was
    exiting. Check the timing before suspecting the code; that is twice in two

v0.10.0 (2026-10-07)  — soupyc STRINGS LEAVE THE 47-CHARACTER CAGE
  Night-queue item 6, first and largest part. docs/next-steps.md has carried
  this as the longest-standing limitation in the tree: a string value was a
  fixed char[48], which is why a soupyc script could not write an ELF.
  - val_t now carries a pointer and a length instead of a buffer. SVAL_LEN
    stays, but only for identifiers and keywords, where 48 is plenty.
  - THE OWNERSHIP QUESTION, which is the whole design. val_t is copied by
    value everywhere - returned from eval_node, stored into variables and
    array slots, passed as arguments - so one string can be referenced from
    several places with no record of how many. Freeing on overwrite would be a
    use-after-free the moment a temporary outlived its slot, and a collector
    cannot help: the temporaries live in C locals, invisible to anything that
    scans the interpreter's own structures. So the store is an ARENA for the
    duration of one script, released in full when the script ends, with a 2 MB
    budget. A runaway loop gets a clean "out of string memory" error instead of
    starving the 8 MB heap that Doom's zone allocator needs.
  - Literals are interned once at parse time and referenced, never copied, so
    a literal inside a loop costs nothing.
  - Everything that used to truncate at 47 now allocates what it needs:
    concatenation, upper, lower, substr, read, input, ai. read() losing its cap
    is the one that matters - a script can now read a file and write it back.

v0.9.5  (2026-10-07)  — TCP, STAGE THREE: CLOSE, AND AN HTTP CLIENT
  Night-queue item 2c, and the end of the TCP arc. `takeout example.com /`
  fetches a page.
  - The close state machine: FIN_WAIT_1, FIN_WAIT_2, CLOSE_WAIT, LAST_ACK and
    TIME_WAIT, with both the active close (we hang up first) and the passive
    one (they do) handled. Our FIN occupies a sequence number, exactly like the
    SYN, and is retired when the peer's acknowledgement reaches snd_nxt.
  - TIME_WAIT lingers 200 ms rather than the two minutes a real stack waits.
    The trade is written down in the file: soupOS uses a fresh ephemeral port
    per connection, so a late duplicate has nothing to be confused with, and a
    shell that froze for two minutes after every close would be unusable.
  - `takeout <host>[:port] [path]`: HTTP/1.0 with Connection: close, so the end
    of the body is the end of the connection and there is no Content-Length or
    chunked decoding to write for a command whose job is to prove TCP works.
  - TWO BUGS, both found by reading a packet capture rather than the code:
      1. The input path began with `if (state != ESTABLISHED) return;`, so the
         moment the peer's FIN arrived we went deaf - including to the
         acknowledgement of data we were still retransmitting. One early return
         caused both symptoms; the capture showed the request going out three
         times while the server sat there having already answered it.
      2. A close that timed out waiting for the peer's FIN marked the
         connection CLOSED and said nothing, leaving it half-open at the other
         end still holding a socket. It now sends a RST, which also stopped the
         gate's listener stalling for five seconds after every `reserve`.
  - A THIRD THING, recorded rather than fixed: three connections in a row to
    the same SLIRP port leave the third unanswered, with no RST and no SYN|ACK.
    Each works alone and the frames are identical, so this is QEMU-side state
    outliving our close. The gate gives each check its own listener port.
  - Gate 45 -> 47 checks: an HTTP page fetched over TCP, and a connection that
    closed cleanly in both directions.

v0.9.4  (2026-10-07)  — TCP, STAGE TWO: DATA
  Night-queue item 2b. `holler 10.0.2.2 19100 souptcp` sends over TCP and
  prints what comes back.
  - Stop-and-wait, and the header says so: one segment in flight, acknowledged
    before the next goes out, retransmitted four times before giving up. No
    congestion control, no window scaling, no selective acknowledgement. An
    out-of-order segment is dropped and re-acked at the old position, which is
    this stack's way of asking for a resend. On a virtual network that costs
    nothing; the comment says it would not be free on a real one.
  - Acknowledgement comparisons use signed arithmetic on the difference
    ((int32_t)(a - snd_una) > 0) rather than a plain >, because the sequence
    space wraps and a naive comparison breaks once the numbers pass 2^31.
  - The receive buffer is filled by the interrupt handler and drained by
    tcp_recv, which takes its snapshot with interrupts off rather than trying
    to be clever with a lock-free ring for one reader.
  - A FIN is acknowledged and noted but not acted on: the close sequence is
    stage 2c. Acking it at least stops the peer retransmitting it at us.
  - Shell: `holler <host> <port> <text>`.
  - Gate 43 -> 45 checks. The gate's listener now echoes what it is sent,
    upper-cased, so a reply proves our segment arrived, was acknowledged, and
    theirs was taken in sequence and handed to the reader. Verified by eye too:
    `souptcp` out, `SOUPTCP` back.

v0.9.3  (2026-10-07)  — TCP, STAGE ONE: CONNECTION SETUP
  Night-queue item 2a. soupOS completes a three-way handshake.
  - src/tcp.c: one connection at a time, the same single-slot model the
    resolver uses, which keeps the state machine in one visible struct instead
    of a table. CLOSED -> SYN_SENT -> ESTABLISHED, SYN retransmitted twice
    before giving up, and a peer RST reported as a refusal.
  - The rule that matters for everything above it: a SYN occupies one sequence
    number. snd_nxt is iss + 1 after sending ours, and rcv_nxt is their seq + 1
    on receiving theirs. Getting that wrong is the classic way to acknowledge
    one short and stall forever.
  - A duplicate SYN/ACK is re-acked rather than ignored, which a packet capture
    showed was needed: the peer retransmits when our ACK is late, and silence
    makes it keep going until it gives up.
  - tcp_close() sends RST, not FIN. The graceful close is stage 2c, and
    pretending otherwise here would leave a half-closed connection nobody
    handles. Said so in the file.
  - Shell: `reserve <host> <port>`, which books a table and releases it.
  - Gate 42 -> 43 checks, hermetic: the gate starts a listener on the host's
    loopback, which the guest reaches through QEMU's 10.0.2.2, so no external
    network is involved.
  - ONE THING LEFT UNEXPLAINED, deliberately. QEMU ignores the first SYN after
    an ARP exchange and answers the retransmit 7 ms later, costing one second
    on the first connect. Both SYNs are byte-identical on the wire, same
    destination MAC, same checksum, so the frame soupOS emits is correct and
    the behaviour is on QEMU's side. Recorded rather than chased.

v0.8.5  (2026-10-06)  — THE PAGE ALLOCATOR WAS NOT SAFE FOR TWO PROCESSES
  pmm_alloc_page() was completely unguarded:

      for (i = 1; i < MAX_PAGES; i++)
          if (!is_used(i)) { set_used(i); used_pages_++; return ...; }

  A read-modify-write on shared state. That was fine while one program ran at
  a time, and stopped being fine in v0.8.0: every proc_spawn calls
  paging_new_dir, and every ELF load and every sbrk calls map_user_page, so
  since then several processes can be inside that loop at once. Two of them
  seeing the same page free hands the SAME physical frame to both, which is
  silent cross-process memory corruption. used_pages_++ has the same window,
  and that counter is what the gate's leak check reads.
  - PROVEN, not assumed. New user/memtest.c fills its own pages with a tag and
    checks them after yielding. Four copies launched by hand never collided,
    because typing the commands staggers them by a second each. Launching them
    as one pipeline starts them microseconds apart, and with a deliberate
    switch inserted between the check and the claim the log read
    "[pmm] RACE: page 2541 was taken while we slept" and the processes died.
    Worth recording what did NOT reproduce it: widening the window with a busy
    spin instead. A collision needs the OTHER task's short scan to land inside
    the window, so stretching the window after the scan barely changes the
    odds. That is also why this is rare in practice rather than constant.
  - FIXED with irq_save/irq_restore around both the claim and the free,
    matching heap.c. Interrupts off rather than a mutex because the critical
    sections are a few instructions, never yield, and no interrupt handler
    allocates, so there is nothing to block on.
  - vfs.c's alloc_node had the same shape of bug: two processes in vfs_open or
    vfs_pipe could both claim one slot in the 16-entry handle table. Guarded
    with preempt_disable, which is enough because the scan never yields.
  - Gate 35 -> 38 checks: three processes started by one pipeline, each
    verifying its own pages survived the others allocating.

v0.8.3  (2026-10-06)  — PIPES, REDIRECTION, AND A SEGMENT BUG FROM v0.7.0
  `cook echo.elf hi | upper.elf | wc.elf` and `cook cat.elf < A.TXT > B.TXT`
  work. Getting there turned up a latent kernel bug that had been waiting since
  ring 3 was introduced.
  - THE BUG. The ISR/IRQ/syscall stubs never touched the segment registers, so
    after a trap from ring 3 the kernel ran on the USER data selector. That was
    survivable only because it is flat, and because segment registers are
    global state that task_switch does not save. The first time a ring-3
    program BLOCKED inside a syscall (which nothing did before pipes), the
    sequence became: the reader blocks; another task runs and leaves DS set to
    the kernel selector (user_mode_exit does exactly that); the reader resumes
    and irets to ring 3 holding a DPL-0 data segment; the CPU nulls every data
    segment whose DPL is below the new CPL; the program's next memory access
    faults; the fault handler faults the same way because DS is null; the
    machine dies with interrupts off before anything can be logged.
    Diagnosed from a register dump showing DS=ES=FS=GS=0000 and QEMU's -d int
    showing no exceptions at all. Each stub now saves the interrupted
    context's data selector, loads the kernel one for the handler, and
    restores it before iret, so the kernel no longer depends on who it
    interrupted. registers_t gains `ds` as its first member to match.
  - FDS 0-2 ARE BINDABLE. An entry in proc_t.ufds wins over the console
    default, so a spawn can be handed stdin/stdout. usermode_run clears the fd
    table from 3 up now, or it would wipe what the spawner just bound.
  - PIPES are a VFS backend: one 4 KB ring shared by two ordinary vfs_node_t
    handles. A reader blocks while the pipe is empty and a writer exists, and
    reads 0 once the last writer closes; a writer blocks while full and a
    reader exists, and fails once every reader closes. Both give up when the
    running process has a kill pending, so a program parked on a pipe nobody
    will write to stays killable, and both enable interrupts to block for the
    same reason proc_take_stop does.
  - THE SHELL runs pipelines: `|` up to 4 stages, `<` and `>` on the ends, a
    trailing `&` for the whole thing. Every stage is checked before any is
    started, the last stage gets the terminal, and the shell waits for it
    first, because it is the one Ctrl-C and Ctrl-Z act on.
  - cat.elf became a filter with no argument; upper.elf and wc.elf are new.
  - fork() was dropped from this milestone with reasons: soupOS's shell lives
    in the kernel, so nothing duplicates itself before exec, and proc_spawn
    already makes a process from nothing. It is worth building the first time
    a user program needs a child.
  - Gate 27 -> 32 checks.
  Design notes: docs/superpowers/specs/2026-10-06-pipes-and-redirection-design.md

v0.8.2  (2026-10-06)  — JOB CONTROL
  Ctrl-Z stops the foreground program and hands the shell back; `steep` resumes it
  in the background, `plate` resumes it in the foreground and waits again. M2 of
  the process milestones.
  - proc_state_t gains PROC_STOPPED. A stopped process is alive, keeps its
    address space, and its task is BLOCKED, so it costs nothing but RAM.
  - It parks at the same three safe points the kill unwind uses, for the same
    reason: no kernel lock is held there, so parking cannot strand a mutex.

v0.8.1  (2026-10-06)  — DOOM IS 23x FASTER
  "Doom runs horribly." It did, for two independent reasons, one in the port
  and one in how QEMU was being started. Both were found by measuring rather
  than guessing: PROFILE=1 builds the port with per-phase rdtsc counters that
  report fps and kilocycles per phase to the serial log every 50 frames.
  - THE PORT. Of 6.13M cycles per frame, draw_flats was 5.45M, or 89%. It
    called find_sector_at() for every floor and ceiling pixel, and that is a
    BSP descent plus four dependent lookups (subsector -> seg -> linedef ->
    sidedef), ~100 cycles, 53,760 times per frame. Real Doom knows the sector
    from the BSP traversal and draws visplanes.
    Along one screen row the visible floor is a straight line in world space,
    so the sector only changes where that line crosses a sector boundary.
    flat_row_runs() samples every 16 pixels and bisects where two samples
    disagree, giving the exact boundary pixel for a few dozen descents per row
    instead of 320. Frame 6.13M -> 1.53M cycles (4.0x); flats 5.45M -> 0.86M
    (6.4x). Verified by screendump: 0 of 256,000 pixels changed.
  - THE HOST. No accelerator was ever requested, so QEMU emulated every
    instruction with TCG. The run targets now probe /dev/kvm and use it when
    it is there, falling back to TCG when it is not. Same scene: 9.9M cycles
    per frame under TCG against 1.53M with KVM.
    The smoke test deliberately stays on TCG and the stock qemu32 CPU: that
    is the configuration whose missing SSE2 caught the v0.7.4 triple-fault,
    and -cpu host would mask that class of bug.
  - Together: 35M cycles per frame before, 1.53M after.
  - TURNING. 32 view angles meant each step rotated the world 11.25 degrees,
    which looks like stop-motion at any frame rate. Now 128 steps of 2.8125
    degrees, with TURN_DELAY 4 -> 1 so the turn rate is unchanged. All the
    derived constants go through ANG_N/ANG_90/ANG_PER_DIR/ANG_SKY_U. The
    spawn frame is pixel-identical to the 32-angle build.
  Not changed, measured and found innocent: the vblank spin (~15k cycles,
  QEMU's default retrace emulation just toggles the bit) and the 64,000-byte
  copy to VRAM (~33k with KVM). Both are rounding errors next to the renderer.

v0.8.0  (2026-10-06)  — CONCURRENT RING-3 PROCESSES
  A program is a process now, not a coroutine the shell runs on its own task.
  Several run at once, background jobs work, and a program that refuses to
  cooperate can be killed.
  - PER-TASK RING-0 STACK. tss.esp0 was set once at boot to a single static
    kstack and tss_set_esp0() was never called at all; kernel_resume_esp was
    one word in .bss. With two programs that is a corruption bug: the timer
    fires while A is in ring 3, the CPU pushes A's frame onto kstack,
    sched_preempt switches away with that frame live, then B syscalls onto the
    same esp0 and lands on top of it. Both are now task_t.user_resume_esp, and
    task_yield moves tss.esp0 with `current`. It is the resume esp, not the
    stack top, because user_mode_enter leaves four saved registers on that
    stack for as long as ring 3 runs. (src/task.c, usermode_asm.asm, gdt.c)
  - NEW src/proc.c + proc.h. A process IS a kernel task (pid == task id), so
    the scheduler, wait queues, mutexes and reaper are reused as-is. proc_t
    holds what used to be file-scope in usermode.c (exit code, fd table, heap
    break, args, page budget, in-user flag) which is exactly what limited the
    machine to one program. 8 static slots, no allocation.
  - The slot outlives the task on purpose: the reaper frees a DEAD task_t and
    its stack, so an exit code kept there would vanish before the parent read
    it. Zombie until proc_wait collects it or the next prompt announces it.
  - exec_elf(path, args) -> usermode_run(proc_t *), called on the process's own
    task. cmd_cook no longer enters ring 3 on the shell task, which is why a
    program that never exits no longer wedges the shell.
  - KILLING. proc_kill only sets a flag; marking the task DEAD would leak the
    whole address space, because the loader would never return to free it. The
    flag is taken where no locks are held: syscall entry/exit, and an IRQ that
    interrupted ring-3 code ((cs & 3) == 3). An IRQ inside the kernel half of a
    syscall must not unwind - it may hold the FAT mutex, and abandoning that
    frame would lock the filesystem forever. The IRQ path is also the only way
    to kill a program that makes no syscalls, which user/hog.c is.
  - Ctrl-C is raised in the keyboard IRQ, the way a tty does it: while a
    foreground program runs the shell is blocked in proc_wait and reads no
    keys. 0x03 flags the foreground process and is swallowed; with no
    foreground process it still cancels the shell's input line.
  - stdin belongs to the foreground process; others read EOF instead of
    stealing keys. That wait is interruptible and sti's first: int 0x80 is an
    interrupt gate, so waiting with IF clear waited forever for the keyboard
    IRQ that fills the buffer. (Nothing had exercised ring-3 stdin before.)
  - mapped[1024]/is_mapped deleted: dedup asks paging_is_mapped, which is
    authoritative, costs no memory and is not O(n) per page. The counter left
    is just the per-process budget.
  - task_count_alive() ignores DEAD tasks, so `doom` no longer refuses to start
    merely because a program finished before the reaper swept it.
  - Shell: `cook prog &`, `orders`, `kill %` (newest process), `ps` marks which
    tasks are processes, finished background jobs announced before the prompt.
  - New user programs: marker.elf (tags every step with its argument, so two
    copies prove concurrency) and hog.elf (loops forever, no syscalls).
  - Gate grew from 14 checks to 22: two processes interleaving, the per-task
    esp0 invariant asserted as two different measured numbers, both kill paths,
    Ctrl-C on a foreground program, shell survival after a kill, and equal free
    page counts across two runs of one program (no address-space leak).
  Design notes: docs/superpowers/specs/2026-10-06-concurrent-processes-design.md
  Still open: fork/exec and pipes, fg/bg and process groups, and the
  preemption-safety debt below (soupyc, vfs, users, shell still have unguarded
  file-scope state).

v0.7.4  (2026-08-25)  — PREEMPTIVE MULTITASKING + GCC 16 BUILD FIX
  The scheduler stops being cooperative-only: IRQ0 now switches tasks.
  (The kernel side of this had been sitting unreleased in the tree since
  2026-06-16; this entry documents it and makes it build again.)
  - Timer-driven preemption. task.c gains `preempt_armed` + `sched_locked`,
    `sched_preempt()`, and `preempt_disable/enable`. irq_handler calls
    sched_preempt() after the IRQ0 EOI with interrupts still off; it switches
    only when preemption is armed, the scheduler is not already locked, and
    more than one task exists. kernel_main arms it after the cooperative
    self-test. (src/task.c, src/task.h, src/isr.c, src/kernel.c)
  - sched_locked balances *across* a context switch: whoever is switched to
    runs the matching sched_unlock (after its own task_switch, or via the
    first-run trampoline task_start), so a running task always observes
    sched_locked == 0.
  - heap.c wraps kmalloc/kfree in irq_save/irq_restore — the free list is
    shared mutable state and a preemption mid-splice would corrupt it.
  - New shell `spinbg`: a CPU-bound task that never calls task_yield. Under
    the old scheduler it froze the box for 4 s; now the shell stays live and
    other tasks keep running. Run `yieldbg` then `spinbg` — the [bg] sleeper
    holds its exact 30-tick cadence straight through the [spin] window,
    which can only happen if IRQ0 is switching tasks.
  - BUILD FIX: added -mgeneral-regs-only to CFLAGS and UCFLAGS. GCC 12+
    auto-vectorises plain byte loops at -O2; on GCC 16 the TSS-zeroing loop
    in gdt_init compiled to `pxor xmm0,xmm0`. The kernel never enables SSE
    (no CR4.OSFXSR / FXSAVE area) and QEMU's default qemu32 CPU does not
    expose SSE2, so that is an invalid opcode — and with no IDT loaded yet
    it went #UD -> #GP -> #DF -> triple fault, before the GDT was even
    installed. The tree had 545 such instructions in the kernel and 83 in
    each user ELF; the flag takes both to zero. Without it soupOS does not
    boot on any modern toolchain.
  - New scripts/smoke-test.sh — headless boot + shell driver (via the QEMU
    monitor, scripts/qemu_keys.py) that greps the serial log for the marker
    each subsystem emits. Exits non-zero on the first miss, so it works as
    a gate. Covers boot, preemption arming, all four ring-3 syscall paths,
    scheduler interleaving, and "did not panic".
  Still open: the non-heap subsystems are not preemption-safe yet — see
  KNOWN BUGS / DEBT.

v0.7.2  (2026-06-16)  — COOPERATIVE SYS_YIELD + SYS_TICKS
  Ring-3 programs can now cooperate with the scheduler.
  - SYS_YIELD is wired to task_yield() (was a no-op). It re-enables
    interrupts first: the int 0x80 gate is a DPL-3 *interrupt* gate so IF

    deadlock with interrupts off. Safe because only one user program runs
    at a time, so the frame left on the TSS (esp0) kernel stack can't be

    user's IF is restored from its saved EFLAGS by iret. (src/usermode.c)

    user program can pace itself in wall-clock time. ulib gains sys_ticks()

  - New program user/spin.c: loops on ticks+yield for ~3 s, emitting [u]
    markers to serial. New shell `yieldbg`: spawns a background task that
    logs [bg] markers every 300 ms via task_sleep. Run `yieldbg` then
    `cook spin.elf` — the [bg]/[u] markers interleave in the serial log,
    which only happens if the ring-3 yield reaches the scheduler. Verified
    headless: bg kept ticking on schedule all through spin's 3 s busy loop.

RESOLVED 2026-08-26 (v0.7.6) — DOOM ENEMY AI
────────────────────────────────────────────────────────────────

The AI was never broken. Diagnosed by instrumenting level_load and
thing_think instead of following the hypotheses that were recorded here,
all of which turned out to be wrong:

  - lv_things and lv_thing_ai both allocate fine. Measured on E1M1:
    nthings=138, lv_things=0x18af98, lv_thing_ai=0x18b508, 552 bytes. No
    heap exhaustion. thing_ai_t is 4 bytes, so that allocation is about
    1 KB; the theory that an 8 MB heap failed it, and the suggested fix of
    shrinking MAX_SPRITES, were both aimed at an allocation orders of
    magnitude larger.
  - thing_think runs every frame and finds all 29 monsters.

The real cause was ENEMY_SEE_D2 = 512*512. In E1M1 the nearest monster
spawns about 816 units from the player start (measured min_d2 = 665920), so
nothing ever woke unless you walked into it. That alone produces every
symptom in the original report: enemies never move toward the player, never
deal damage, and the walk cycle never starts.

Widening the radius then exposed the bug the small radius had been hiding:
there was no line-of-sight test anywhere in the AI. Every woken monster
could shoot the player from any distance, through walls, so raising SEE_D2
made the whole map converge and kill the player in about a second (health
100 -> 10 in 120 ticks).

Fixed:
  [x] los_clear() + seg_crosses() in doom.c — segment intersection against
      one-sided linedefs, int64 throughout. Both waking and the ranged
      attack are gated on it, so monsters neither notice nor shoot through
      walls. Two-sided lines count as see-through, so a monster can see
      through a closed door; a known simplification.
  [x] ENEMY_SEE_D2 raised to 1024*1024 so enemies engage at all.
  [x] ENEMY_RNG_D2 (768*768) bounds the ranged hitscan. Chasing stays
      unbounded; only shooting is limited.
  [x] thing_think's distance math moved to int64, matching fire_weapon.
      dx*dx + dy*dy overflows int32 across a large map and can go negative,
      which would make the proximity test pass for distant things.
  [x] fire_weapon now checks the level is loaded BEFORE spending a round.
      The old order decremented ammo and then bailed, which is exactly the
      reported "ammo decrements but nothing happens".

Verified in QEMU from status bar readings across one run: 050 ammo / 100%
health at spawn, 050 / 085% after approaching, 041 / 050% after firing nine
rounds. Enemies wake on sight, close distance, and deal damage at a
survivable rate. Death now requires pushing into a room and fighting rather
than happening within a second of spawn.

Not directly confirmed: a monster dying from player fire. Shots are fired
and ammo decrements, but no test drove a single enemy to zero HP.

Also fixed earlier, by the 2026-08-25 vga13h work rather than here: the
death/level-complete screen no longer shows garbled rainbow pixels, because
restore_regs restores all 768 DAC bytes on exit from mode 13h.

All four steps are done. Step 3 landed in v0.7.0: soupOS runs ring-3

────────────────────────────────────────────────────────────────
THE LLM  (aka the funniest possible feature)
────────────────────────────────────────────────────────────────

The idea: type `ai <prompt>` at the soupOS shell and get an
actual LLM response — from inside a 32-bit hobby OS.

Obviously we can't run a real LLM in-kernel. Here are three
approaches ranked from "actually works" to "maximum chaos":

─── OPTION A: Serial Port Bridge (most practical) ───────────────

QEMU can expose the serial port as a PTY or TCP socket instead
of logging to a file:

  qemu-system-i386 ... -serial pty
  # or
  qemu-system-i386 ... -serial tcp:127.0.0.1:4321,server

On the host side, a tiny Python daemon listens on that socket,
receives the prompt, fires it at Ollama (or the Claude API), and
streams the response back character by character.

Kernel side:  [DONE — shipped in v0.6.4]
  [x] UART driver — polled COM2 (0x2F8), bidirectional (serial2_* in
      serial.c). Probed via the scratch register; IRQ-driven RX is still
      possible future work but polling+yield is plenty at 38400 baud.
  [x] `ai_send(prompt)` — writes "<prompt>\n" to COM2 (ai.c)
  [x] `ai_getc(timeout)` — reads reply bytes until 0x04 (EOT)
  [x] `ai` shell command: reads args, calls send/recv, prints
  [x] Response streams in real-time (one char at a time from UART)

This is surprisingly doable. The OS just needs to talk serial;
all the heavy lifting happens on the host. Latency would be the
same as any Ollama query.

Makefile target `run-ai` would launch QEMU with the TCP serial
and auto-start the Python bridge daemon.

─── OPTION B: Tiny Baked-In Markov Brain ────────────────────────

Train a character-level Markov chain (order 4) on soup recipes,
kernel source code commentary, and BOFH excuses. Bake the
transition table directly into the kernel binary as a C array.

  [ ] 26^4 = 456,976 states × a few bytes each ≈ ~2 MB table
  [ ] `markov_generate(seed_str, length)` function
  [ ] Responds with convincingly soup-flavored nonsense
  [ ] Fits in a single .c file with a big static array
  [ ] Totally offline, no network needed
  [ ] Response quality: absolute garbage (this is the point)

Shell command: `ai <prompt>`
  soupOS> ai why is the kernel crashing
  > The broth requires additional simmering. Have you considered
    reallocating the stack noodles? A page fault at 0x0 indicates
    insufficient seasoning in the GDT descriptor soup.

─── OPTION C: GGML Micro-Inference (maximum chaos) ─────────────

Run actual neural network inference in kernel mode, in 32-bit
protected mode, with no FPU (just integer math).

  [ ] Port llama.c / ggml to freestanding 32-bit C
  [ ] Use 1-bit or 2-bit quantization to fit a model in ~8 MB
  [ ] Store weights as a file on the FAT disk (BRAIN.BIN)
  [ ] Load into heap at boot, run inference in-kernel
  [ ] No OS overhead — inferring at near-bare-metal speed

Model candidate: a tiny GPT-2 variant (~10M params, INT4) or
a purpose-trained 1M-param "soupOS assistant" fine-tuned on
the kernel source and soup recipes.

Estimated RAM: 8–16 MB for weights + ~2 MB for activations.
The VM boots with 128 MB so this is technically feasible.
Tokens per second: probably 0.2–2 tok/s on a modern host.
Vibes: 11/10.

─── RECOMMENDED PLAN ────────────────────────────────────────────

  Phase 1 — Ship Option A (serial bridge). Fast to implement,
            gives a real LLM, great demo.
  Phase 2 — Add Option B as a fallback for when the bridge is
            not running ("offline mode"). The garbage output is
            its own reward.
  Phase 3 — Option C for the README hall of fame entry.

soupyc integration (all options):
  [x] ai(prompt)  — soupyc builtin that calls the AI and returns
                    the response as a string (v0.6.4; capped at 47 chars)
  [ ] Allows writing soupyc scripts that use the LLM as a
      subroutine, which is the most unhinged use of a hobby OS
      scripting language imaginable.

  Example:
    let question = "explain paging in one sentence"
    let answer = ai(question)
    pour answer
    beep 440 100

KNOWN BUGS / DEBT
────────────────────────────────────────────────────────────────

  [ ] PREEMPTION SAFETY — the big one. v0.7.4 armed IRQ0 preemption but
      only heap.c was made safe (irq_save around the free list). Every
      other subsystem with file-scope mutable state is now interruptible
      at any instruction: fat.c (44 statics), soupyc.c (69), ata.c (9),
      vga.c (8), plus vfs/users/shell. Two tasks in fat_write, or a
      background task printing while the shell redraws, are data races.
      The cooperative design put yields at chosen points; IRQ0 removed
      that guarantee. Needs either a big-kernel-lock (preempt_disable
      around driver entry points) or per-subsystem locks.
  [x] A ring-3 fault panics and halts the kernel instead of killing the
      program. FIXED: isr_handler checks `(cs & 3) == 3 && usermode_in_user()`
      and calls usermode_fault(), which unwinds into the loader so the program
      dies with exit code -(128 + exception) and the shell lives. v0.8.0 reuses
      that same unwind for kills. `cook crash.elf` is the demo.
  [x] RECIPE.TXT shows "FAT16 read-only" — update the string now
      that write is supported
      (already fixed in `recipe` cmd; also bumped README.TXT to v0.4.0)
  [x] Tab completion only matches filenames, not command names
  [x] shell_tab_complete rescans FAT on every Tab press — cache it
      WON'T DO, measured v0.10.4: a directory scan is 1.9 ms on a normal root
      and 5.5 ms on a 128-entry one, far below what anyone can feel. A cache
